# Архитектура OneTable

План опирается на чат [«Архитектура SaaS платформы»](https://chatgpt.com/c/6b04a717-70f0-83eb-a0b2-32481020f7ed) и локальную схему действующего Doyle. В Doyle админка, экран и приложение игрока уже покрывают полный цикл. Связка через `rooms.state` полезна для текущего клуба. При нескольких клубах, администраторах и планшетах основной риск возникает в момент записи: кто может менять конкретный стол, кому достанется свободное место и сколько раз будет начислено реэнтри после сетевого сбоя.

## Ближайший этап

Перерисовка существующих экранов Doyle в дизайн-системе OneTable. Для этого этапа сохраняем действующий Supabase, таймер и его синхронизацию. TypeScript и Vite можно вводить постепенно при выделении общих компонентов и логики. Для ТВ и простого планшета подходит небольшой интерфейс на HTML, CSS и TypeScript. Расширенная рассадка и отдельный Node API относятся к дальнейшему развитию. Локальная версия позволяет посмотреть сценарии заранее.

Локальная реализация лежит в `src/` (React-экраны), `shared/model.ts` (контракты), `server/tournament.ts` (серверные команды и проекции), `server/seating.ts` (расчёт плана мест), `server/schema.sql` (ограничения PostgreSQL). `vite.config.ts` подключает локальный HTTP-адаптер. В пилоте точки входа кабинета и планшета можно сохранить, а адаптер вынести в отдельный Node API.

## Вход в клуб

Корень `app.onetable.pro` открывает форму входа или перенаправляет в кабинет
`/clubs/:clubId`. Если у сотрудника несколько активных членств, переключатель клуба
сохраняет выбор в текущей сессии. Ссылка на кабинет открывает указанный клуб после
входа с проверкой членства и роли.

Запросы кабинета передают ID клуба из адреса. Сервер проверяет его при каждом
запросе, поэтому вкладки двух клубов сохраняют собственный контекст. Рабочие данные
клуба Doyle берутся из его действующей базы. Доступ к этой интеграции определяется
привязкой учётной записи на сервере.

## Одна игра на нескольких экранах

В локальной реализации турнир создаётся на маршруте клуба `POST /api/clubs/:clubId/tournaments`. Транзакция сохраняет черновик, копию параметров и структуры выбранного макета, начальное состояние таймера, места и журнал. Повтор команды возвращает ID уже созданного черновика. Клубные макеты хранятся в `blind_presets` по ключу клуба и имени. Существующие шаблоны блайндов доступны как макеты структуры.

Жизненный цикл проходит через `draft → scheduled → live → finished`. Черновик виден только администратору. Отдельная команда публикации проверяет дату и время и переводит ту же запись в расписание, доступное через `GET /api/public/clubs/:clubId/schedule`. В проекцию расписания входят сведения для игроков: состояние, название, дата, описание, формат, взнос и стартовый стек. Регистрации, рабочий экран, таймер, планшет и ТВ используют исходный ID турнира. Время начала в расписании хранится отдельно от времени запуска отсчёта. Миграция сохраняет статусы существующих записей.

Онлайн-запись и очередь используют `entries` того же турнира. Место в очереди определяется временем записи. Отметка прихода в очереди сама по себе не создаёт начисление. При допуске администратором проверка поздней регистрации, очереди и ёмкости, назначение места, начисление и журнал выполняются в одной транзакции под той же блокировкой, что и вылет и ручная рассадка. Публичный API возвращает только статус и позицию игрока по ключу браузера. Для пилота этот ключ нужно заменить проверенной идентификацией игрока.

Выбор аддона хранится как один из трёх вариантов. Смена варианта отменяет прежнее начисление и создаёт новое с ценой выбранного пакета. ТВ суммирует зафиксированные при выдаче фишки. Обычные аддоны из существующих записей мигрируют в первый вариант.

Администратор работает на странице турнира. Столы, игроки, таймер и журнал используют одну версию состояния. CRM живёт на маршруте клуба, поскольку карточка и долг охватывают несколько турниров. Планшет дилера открывает один стол. ТВ получает отдельную проекцию с блайндами, временем и агрегатами. Игрок открывает знакомую ссылку своего клубного бота, а темы и вкладки определяются настройками клуба.

Планшет отправляет команду со своим идентификатором. Сервер проверяет членство, назначение на конкретный стол и текущее состояние игрока. В одной транзакции вылет освобождает место и добавляет запись в журнал. Реэнтри возобновляет участие, создаёт начисление и возвращает игрока в очередь. Отдельная оплата уменьшает долг. Повтор команды с тем же идентификатором возвращает сохранённый результат. Состав стола и журнал доступны для сверки после переподключения.

Авторассадка на первом этапе заполняет свободные места и выравнивает долю занятых мест между столами. При равной заполняемости используются номер стола и места. В пилоте нужна очередь по времени прихода и настройка правил случайной первоначальной рассадки. Балансировка игры и расформирование столов потребуют учёта позиции относительно большого блайнда, предварительного плана пересадок и подтверждения флором. При конфликте версий сервер пересчитает план по актуальному составу.

Для турнирной истории выделить отдельные входы игрока, каждую посадку и перемещение, порядок вылетов и финальный результат. Локальная версия пока хранит текущую запись игрока, счётчик реэнтри, последние назначения и журнал. Для пересчёта результатов эти данные нужно расширить отдельными таблицами. Участники, начисления и посещения связываются по клубному идентификатору игрока, чтобы одинаковые имена из разных клубов не пересекались.

## От локальной версии к пилоту

1. **Серверное окружение.** Развернуть отдельный PostgreSQL/Supabase для OneTable. Добавить площадки, членство, роли администратора, флора, дилера и владельца. Привязать дилера к *конкретному* турниру и столу. Заменить демонстрационные профили на Supabase Auth и клубные назначения. Настроить RLS и закрытые каналы с проверками членства. Включить версию записи игрока в чувствительные команды и отправлять уведомления о событиях после фиксации транзакции. ТВ получает токен с правом чтения узкой проекции.
2. **Два тестовых клуба.** Настроить лимиты и стоимость входов/реэнтри, структуру уровней, площадки, состав столов и правила рассадки. Добавить результаты, рейтинг, лист ожидания, бонусы, отмены и возвраты с журналом. Подключить два тестовых Telegram-бота с серверной проверкой подписанных данных для своего бота. Пройти запись → приход → место → вылет → реэнтри → оплата → итог в профиле игрока.
3. **Перенос из Doyle.** Подготовить импорт копии данных в стенд. Сохранить соответствие старых и новых ID, сверить число визитов, суммы и результаты. Отдельно обработать ручные записи из `rooms.state` без ID игрока. Сверять привязку с оператором по источникам и идентификаторам. Переносить активные турниры только по отдельному проверенному сценарию переключения.
4. **Внешний пилот.** Выпустить одну версию платформы для двух клубов с разными темами. Единый API поддерживает стандартные шаблоны приложения и дисплея, для индивидуальных экранов нужна совместимость API. Сначала включать релиз тестовому клубу. Во время игры использовать обратно совместимые миграции и восстановление по полному снимку после разрыва соединения. Тариф и модули хранить в настройках клуба, ограничения применять после активного турнира.
5. **BIG GAME и подписка.** Подключить CRM Pro с импортом, воронкой и аналитикой после базового пилота. Проверить доступ к перепискам на реальных аккаунтах до оценки сроков интеграции. На старте учитывать подключение и срок подписки вручную. Автоматические списания подключить после отработки пилота.
